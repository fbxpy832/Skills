# Deep Research

深度研究参谋技能——面向企业经营、技术研发和项目落地的复合型深度研究框架。

## 覆盖领域

本 Skill 适用于以下 11 类研究课题：

| 编号 | 领域 | 典型课题 |
|------|------|---------|
| D1 | 算法技术路线 | 视觉算法选型、端侧模型架构、Agent 方案对比 |
| D2 | 应用开发方案 | 技术栈评估、系统架构决策、API/SDK 选型 |
| D3 | 需求分析 | 市场缺口识别、用户痛点挖掘、需求优先级排序 |
| D4 | 热点概念辨析 | 新术语定义、技术范式变迁、伪概念识别 |
| D5 | 产业趋势 | 赛道格局、产业链分析、技术成熟度曲线 |
| D6 | 资本市场动态 | 投融资事件、上市公司分析、估值逻辑 |
| D7 | 政策/政府项目 | 政策解读、专项资金申报、政府采购标准 |
| D8 | 竞品与标杆案例 | 竞争对手方案、行业最佳实践、差异化定位 |
| D9 | 工程实施与系统架构 | 部署方案、性能评估、可扩展性分析 |
| D10 | 商业模式与运营机制 | 盈利模式、定价策略、运营指标体系 |
| D11 | 综合/交叉 | 涉及多个领域的复合型课题 |

## 核心原则

1. **先分类，再研究** — 识别问题类型和受众，确定研究深度和方向
2. **先框架，再搜索** — 建立问题树后分层搜索，而非盲目搜索
3. **先验证，再结论** — 证据分级、反证扫描、交叉验证之后才形成观点
4. **一手优先** — 政策、技术、公司、市场等关键信息必须追溯一手来源
5. **直面反面** — 主动搜索反证，报告中如实呈现分歧和不确定性
6. **落地导向** — 所有研究最终服务于决策和行动建议
7. **禁止空话** — 建议必须包含动作主体、具体动作、所需资源、时间节奏、预期结果、风险条件。避免"加强、推动、赋能、构建生态"等空泛表达

## 输出深度控制

| 级别 | 字数 | 适用场景 |
|------|------|---------|
| 简版 | 3000-5000 字 | 普通概念解释、快速了解新领域、给非技术读者的概览 |
| 标准版 | 8000-12000 字 | **默认级别**。大多数研究场景 |
| 深度版 | 15000 字以上 | 重大决策支撑、深度技术选型、投融资尽调 |

未指定时默认标准版。普通概念解释可自动降级为简版。

## 研究流程

### Phase 1：研究目的识别

收到研究请求后，依次自动识别以下维度。除非缺失信息会导致研究方向完全不同，否则不追问，按默认值执行并在报告中标注假设。

#### 1.1 问题类型自动分类

| 类型 | 特征关键词 | 输出侧重 |
|------|-----------|---------|
| 认知类 | "什么是""介绍一下""解释" | 概念辨析、背景脉络 |
| 选型类 | "选哪个""对比""选择" | 多维度对比、适用条件 |
| 趋势类 | "趋势""走向""未来""方向" | 演进脉络、驱动因素 |
| 决策类 | "该不该""要不要""是否值得" | 可行性、ROI、建议 |
| 方案类 | "方案""怎么做""如何实现" | 架构设计、实施路径 |
| 对标类 | "参照""和 X 比""竞品" | 差异化分析、优劣势 |
| 诊断类 | "为什么""根源""问题出在哪" | 根因分析、症结识别 |
| 报告类 | "写报告""汇报""整理" | 格式合规、受众适配 |
| 监测类 | "最新""最近""近期进展" | 时效性优先、动态追踪 |

#### 1.2 受众层级识别

| 受众 | 报告要求 |
|------|---------|
| 工程师/研发团队 | 技术细节、性能数据、实现方案 |
| 技术管理者 | 技术权衡、资源投入、团队能力匹配 |
| 企业管理者 | 商业价值、竞争格局、ROI |
| 政府主管部门 | 政策合规、社会效益、标准符合 |
| 集团/国企上级领导 | 战略对齐、风险可控、可批复性 |
| 投资人/资本市场 | 市场空间、增长潜力、竞争壁垒 |
| 客户/合作伙伴 | 价值主张、案例佐证、合作模式 |

#### 1.3 决策锚点自动识别

扫描请求中包含以下哪些决策意图，标记为重点回答方向，在报告对应模块中深度展开：

- `[是否立项]` — 该方向是否值得启动项目
- `[是否投入研发]` — 是否分配研发资源
- `[是否采购合作]` — 是否引入外部方案/供应商
- `[是否选择技术路线]` — A/B/C 方案如何选择
- `[是否进入赛道]` — 是否进入该市场/领域
- `[是否对外汇报]` — 报告用于对外沟通/展示
- `[是否形成开发任务]` — 是否拆解为开发工作项
- `[是否用于投融资判断]` — 辅助投资/融资决策

#### 1.4 时间范围与搜索策略绑定

| 时间标签 | 范围 | 搜索策略 |
|---------|------|---------|
| 即时/监测 | 最近 1-3 个月 | 优先新闻/动态/GitHub 活跃仓库/最新论文 preprint |
| 短期决策 | 近 3-6 个月 | 优先近期论文、产品动态、行业报告 |
| 中期规划 | 1-2 年 | 综述论文+中期趋势报告+公司战略文件 |
| 长期趋势 | 3-5 年 | 经典文献+权威展望报告+学术 survey |
| 基础理论 | 不限 | 优先原始论文、经典教材、权威来源 |

#### 1.5 缺失信息处理规则

| 缺失项 | 默认值 |
|--------|-------|
| 受众 | 企业管理者/技术管理者（综合性报告） |
| 输出格式 | Markdown 深度报告 |
| 输出深度 | 标准版（8000-12000 字） |
| 地域范围 | 中国市场优先，全球对标补充 |
| 是否结合公司业务 | 默认结合智慧停车、端侧 AI、城市治理平台、郑好停/阿顺数智做落地启发 |
| 引用偏好 | 偏好一手来源、权威来源，二手来源注明转引 |

#### 1.6 联网与引用规则

涉及以下内容时，必须联网检索最新信息并标注来源：

- 政策法规、政府文件
- 市场数据、行业规模
- 公司信息、产品动态、价格
- 投融资事件、估值
- 学术论文、技术预印本
- 开源项目、Star 数、活跃度
- 新闻事件、热点话题

引用格式：`来源: [标题](URL) | 获取日期: YYYY-MM-DD`

### Phase 2：建立问题树

将研究课题分解为 3 层问题树：

```
根问题: [用户原始请求]
├── 第 1 层：核心子问题（必须回答，3-5 个）
│   ├── 子问题 1：定义与边界（是什么、范围）
│   ├── 子问题 2：现状与格局（谁在做、做到哪了）
│   ├── 子问题 3：关键判断点（成败关键、核心变量）
│   └── 子问题 4：与我关系（对公司的意义）
├── 第 2 层：支撑子问题（为第 1 层提供论据）
│   ├── 技术可行性、市场验证、成本区间等
│   └── 根据问题类型动态生成
└── 第 3 层：深挖节点（根据初步搜索结果展开）
    └── 搜索过程中发现的关键延伸点
```

问题树在搜索过程中动态更新——发现新的关键子问题则追加，确认无关则剪枝。

### Phase 3：分层搜索

#### 3.1 四层搜索策略

**L1 - 全貌扫描**（快速定位）
- 目标：了解领域全貌、关键玩家、核心概念
- 手段：WebSearch + 维基百科 / Survey 论文 / 行业报告摘要
- 输出：领域概览 + 关键关键词列表

**L2 - 定向深挖**（聚焦关键子问题）
- 目标：对每个核心子问题获取足够深度信息
- 手段：定向搜索 + arxiv / PapersWithCode / 公司官网 / 行业报告
- 输出：每个子问题的结构化信息块

**L3 - 一手验证**（核实关键论断）
- 目标：对核心论断追溯一手来源
- 手段：原始论文 / 官方文档 / 政府文件 / 财报 / 一手数据
- 输出：可信度评估 + 直接引用

**L4 - 反证扫描**（主动找反面证据）
- 目标：主动搜索与初步结论相悖的信息
- 手段："XX 失败"、"XX 局限性"、"XX 替代方案"、"XX 质疑"
- 输出：反面论点清单 + 对主要结论的修正

#### 3.2 搜索源优先级矩阵

| 信息类型 | 首选源 | 备用源 | 避免 |
|---------|-------|-------|------|
| 学术论文 | arxiv / 顶会论文集 | Google Scholar / 知网 | 非 peer-review 博客 |
| 技术方案 | 官方文档 / GitHub | 技术博客 / 开发者论坛 | 营销软文 |
| 市场数据 | 券商研报 / 咨询报告 | 新闻引用 | 自媒体推测 |
| 公司信息 | 官网 / 财报 / 招股书 | Crunchbase / 天眼查 | 二手传闻 |
| 政策法规 | 政府官网 / 官方文件 | 权威媒体解读 | 个人解读 |
| 产品体验 | 产品本身 / 用户评价 | 评测文章 / 演示视频 | 广告 |
| 开源项目 | GitHub / GitLab | 技术评测 | 未维护项目 |
| 竞品动态 | 官网 / 产品文档 | 行业媒体 / 招聘信息 | 匿名爆料 |

#### 3.3 并行子代理分治

对于包含多个独立子问题的研究课题，启动并行子代理：

- 每个子代理独立负责 1-2 个子问题
- 子代理必须加载 `web-access` skill 进行联网搜索
- 每个子代理返回结构化结果：问题 + 关键发现 + 来源 + 置信度
- 主代理汇总后进行交叉验证

### Phase 4：证据分级、反证扫描与交叉验证

#### 4.1 证据分级标准

| 级别 | 定义 | 标记 |
|------|------|------|
| **S 级** | 一手权威来源：原始论文、官方文档、政府文件、原始数据、财报 | `[S]` |
| **A 级** | 经严格审查的二手来源：权威 survey 论文、知名机构报告、顶会文章 | `[A]` |
| **B 级** | 较可靠二手来源：正规媒体报道、知名技术博客、行业分析 | `[B]` |
| **C 级** | 一般来源：个人博客、论坛讨论、未经验证的数据、社交媒体 | `[C]` |
| **D 级** | 推测/传闻：未经证实的消息、匿名来源、硬伤明显的文章 | `[D]` |

**规则**：
- S/A 级证据可作为核心论断支撑
- B 级证据需至少 2 个独立来源交叉验证
- C 级证据仅用于方向判断，不用于关键结论
- D 级证据标注"未证实"，不纳入结论

#### 4.2 引用分级：事实引用 vs 观点引用

| 引用类型 | 定义 | 要求 |
|---------|------|------|
| 事实引用 | 客观可验证的信息：数据、日期、价格、规格、事件 | 必须引用 A/B 级以上来源 |
| 观点引用 | 主观判断：预测、评价、趋势判断、建议 | 可引用 C 级来源，但必须标注出处 |

**规则**：
- 关键事实必须引用 A/B 级来源
- C/D 级来源只能作为观点参考，不得单独支撑核心结论
- 观点引用前必须注明："以下观点来自[来源]，尚未独立验证"

#### 4.3 时间衰减因子

- 政策法规：以最新发文为准，旧版标注"已废止/已更新"
- 技术论文：1 年内为高价值，2-3 年为参考，3 年以上需确认未被推翻
- 市场规模：以最近年份为准，超过 2 年的数据标注"历史数据"
- 公司信息：超过 6 个月的需确认是否过时

#### 4.4 反证扫描规则

针对主要结论，强制执行反证扫描：

1. 结论的反面假设是什么？
2. 是否存在支持反面假设的证据？
3. 是否有知名人物/机构对该方向提出过质疑？
4. 该技术/方案有哪些已知局限性和失败案例？
5. 如果结论错了，最可能错在哪里？

反证扫描结果必须体现在最终报告中，作为"风险与约束"部分的依据。

#### 4.5 交叉验证规则

- 单一来源的关键论断必须找到至少 1 个独立来源佐证
- 多方来源冲突时，标注分歧并分析原因
- 无法验证的论断，标注 `[待核实]`
- 所有矛盾点必须在报告中体现，不能选择性忽略

#### 4.6 量化数据约束

凡涉及以下类型的数据，必须标注来源和统计口径；无可靠来源时标注为推测值，不得作为核心结论依据：

| 数据类型 | 示例 | 标注要求 |
|---------|------|---------|
| 价格/费用 | 设备单价、服务费、部署成本 | 来源 + 时间 + 报价条件 |
| 性能指标 | 精度、延迟、吞吐、功耗 | 来源 + 测试环境 + 数据集 |
| 市场规模 | 赛道规模、增长率、份额 | 来源 + 统计口径 + 年份 |
| 周期/进度 | 实施周期、开发工期 | 来源或估算依据 |
| 预算/投入 | 研发投入、采购预算 | 来源或估算假设 |

**规则**：
- 有可靠来源（A/B 级）→ 标注 `[来源: XXX, YYYY年]`
- 经验估算 → 标注 `[经验估算]`，且不得作为核心论断的唯一支撑
- 假设值 → 标注 `[假设值: 基于 XX 假设]`，保持假设值可追溯
- 无任何依据 → 标注 `[待验证]`，仅在背景描述中提及，不纳入结论

**示例**：
```
正确: 单路端侧相机成本约 1500-3000 元 [来源: 海康威视 2025 年产品目录，批量 100+ 台]
正确: 假设单路成本 2000 元，1000 路总投入约 200 万 [假设值: 基于上述单价估算]
错误: 端侧相机成本很低，性价比高（无来源、无数据）
```

#### 4.7 技术路线对比约束

涉及算法、系统架构、硬件选型、工程方案、产品路线对比时，禁止只给出单一路线结论。必须按以下结构展开：

**输出结构**：

```
## [方案/路线] 对比分析

### 主推路线
- 方案描述
- 适用条件（什么场景下选它）
- 优缺点（至少各 2 点）
- 资源要求（人才/算力/数据/预算）
- 风险约束

### 备选路线
- 同上完整结构

### 不建议路线
- 方案描述
- 为什么不建议（具体原因）
- 什么条件下可能反转（"如果 XX 变化，可重新考虑"）
```

**规则**：
- 任何时候提到"推荐 X"，必须同时说明替代方案和排除方案
- 不设"无脑推荐"，每条路线必须绑定适用条件
- 所有路线必须附带风险/局限性说明

**示例**：
```
主推: YOLOv8-nano + RK3588
  - 适用: 路侧高位视频，单设备功耗<5W，无需 GPU 服务器
  - 优点: 成熟度高/社区活跃/INT8 量化工具链完善
  - 缺点: 大角度车牌识别率低于 ViT 方案约 2%
  - 资源: 2 人月模型适配，需 5 万+训练样本

备选: EdgeNeXt + RT-DETR-nano
  - 适用: 新项目可跳过 CNN 直接上轻量 ViT
  - 优点: 精度更高/泛化能力更强
  - 缺点: 端侧推理延迟比 CNN 高 30-50%/量化工具链未成熟
  - 风险: 芯片算力需求更高，部分老芯片不支持

不建议: 直接上 YOLOv11x 全精度模型
  - 原因: 端侧芯片无法满足算力和显存需求
  - 反转条件: 若设备升级为 Jetson Orin 级别以上可重新评估
```

#### 4.8 置信度标注

| 标记 | 含义 | 条件 |
|------|------|------|
| `[高置信度]` | 多源 S/A 级证据一致 | ≥3 个独立 S/A 来源 |
| `[中高置信度]` | S/A 级证据但来源有限 | 1-2 个 S/A 来源 |
| `[中等置信度]` | B 级证据且多方验证 | ≥3 个 B 级来源交叉验证 |
| `[中低置信度]` | 信息有限或来源级别不高 | 1-2 个 B 级来源或 C 级多方 |
| `[低置信度/推测]` | 推测性判断 | 缺乏直接证据，基于逻辑推理 |

### Phase 5：观点形成与分析

#### 5.1 观点形成方法

```
证据集合 → 发现模式 → 识别共识/分歧 → 判断可信度 → 形成判断 → 标注置信度
```

**原则**：
- 不盲从权威：即使用 S 级来源，也考虑其局限性和适用场景
- 不追求全票通过：合理分歧是正常现象，在报告中如实呈现
- 区分"事实"与"解读"：事实是客观证据，解读是基于事实的推理
- 标注不确定性：对于没有明确证据支持的判断，明确标注为推测

#### 5.2 业务启发框架

1. **关联度评估**：该研究与公司业务的直接/间接关联程度
2. **切入机会**：公司可以从哪个角度切入
3. **能力匹配**：公司现有能力是否覆盖，差距在哪
4. **竞争定位**：相对于竞品/替代方案的优势和劣势
5. **时间窗口**：现在做是否合适，有无窗口期
6. **资源需求**：需要什么资源（人/钱/时间/数据/合作伙伴）

#### 5.3 风险识别维度

- 技术风险（可行性、成熟度、技术债务）
- 市场风险（需求真实性、竞争烈度、替代风险）
- 政策风险（合规要求、政策变动）
- 执行风险（团队能力、资源约束、时间压力）
- 财务风险（投入产出比、资金链、定价风险）

#### 5.4 行动建议分级（禁止空话规则）

所有建议必须包含：**动作主体 + 具体动作 + 所需资源 + 时间节奏 + 预期结果 + 风险条件**

避免：加强 XX 建设、推动 XX 发展、赋能 XX 转型、构建 XX 生态、筑牢 XX 基础 —— 这些在报告中视为无效内容，必须替换为具体可执行描述。

**短中长期行动**：

| 周期 | 要求 | 示例（正确） | 示例（错误） |
|------|------|------------|------------|
| 短期 1-3 月 | 可验证的具体动作 | "研发团队 3 人用 2 个月完成端侧模型裁剪 POC，需标注数据集 X，验证精度损失<3%即立项" | "加强端侧 AI 布局" |
| 中期 3-12 月 | 有明确里程碑 | "Q2 完成方案选型，Q3 启动开发，年底前上线试点" | "推动项目落地" |
| 长期 1 年+ | 分阶段路径 | "第一年搭建基础平台，第二年扩展场景，第三年形成壁垒" | "构建核心竞争力" |

**确定程度标记**：

| 标记 | 条件 |
|------|------|
| `[立即执行]` | 高置信度 + 低风险 + 与业务高度相关 |
| `[建议推进]` | 中高置信度 + 可控风险 |
| `[保持关注]` | 中等置信度或目前不适合行动 |
| `[暂不建议]` | 低置信度或高风险或不适合公司现状 |
